# 机器人守护进程 —— 总体架构

状态：草稿 · 日期：2026-07-22 · 负责人：pierre

顺序和里程碑在 [`roadmap.md`](../project/roadmap.md)。

[`updater-design.md`](updater-design.md) 的伴侣，它详细覆盖更新系统。本文档覆盖服务拆分、服务如何互相交谈、状态住在哪，以及机器人如何被控制——本地地、从 App、以及远程地。

范围说明：这描述的是**首个发布版本**要去的地方，不是当前原型（`microduck_runtime`，它是探索性的、会被重写）。v1 目标是**单一、明确指定的硬件配置**。

## 它的形状

一块板上的七个守护进程，通过 unix 套接字交谈。其中一个驱动机器人；另外三个的存在是为了让第一个坏了时板子仍可到达，剩下的是一些什么都不拥有的传输和传感器。

```text
   游戏手柄          手机          你，在笔记本上     一个对端，任何地方    一个 GitHub 发布
      │ BLE/USB        │ BLE             │ ssh                 │ WebRTC              │ https
      ▼                ▼                 ▼                     ▼                     │
  ┌────────┐      ┌────────┐       ┌──────────┐          ┌──────────┐                │
  │  padd  │      │  btd   │       │ robotctl │          │  mediad  │                │
  └───┬────┘      └───┬────┘       └────┬─────┘          └────┬─────┘                │
      │               │  同一 API 的一个子集             │                      │
      │  robot.*      │  robot.health · update.* · net.* · pad.* · system.*           │
      ▼               ▼                 ▼                     ▼                      │
  ┌──────────────────────────────────────────────────────────────────┐               │
  │  每个服务一个 unix 套接字 · JSON-RPC 2.0，一行一个对象  │               │
  └────┬──────────────────────┬─────────────────────────┬────────────┘               │
       ▼                      ▼                         ▼                            │
  ┌───────────┐        ┌─────────────┐           ┌─────────────┐                     │
  │  robotd   │        │  configd    │           │  updaterd   │◄────────────────────┘
  │ robot.*   │        │ net.* pad.* │           │ update.*    │
  │ 50 Hz     │        │ system.*    │           │ verify      │
  │ loop      │        │ wifi, name, │           │ swap        │
  │ safety    │        │ pad bonding │           │ health gate │
  └─────┬─────┘        └──────┬──────┘           └──────┬──────┘
        │ Dynamixel           │ D-Bus                   │ systemctl restart,
        ▼                     ▼                         │ then robot.health
  15 servos + IMU      BlueZ · NetworkManager           ▼
  on one UART                                    /opt/robot/daemon/current

  ┌ 发布、不应答任何东西 ───────────────────────────────────────┐
  │  tofd —— 头部的 8×8 深度矩阵，在 /run/tofd/tof.sock。       │
  │         mediad 和 robotd 读它；它不读任何人。               │
  └───────────────────────────────────────────────────────────────────┘
```

**`robotd` 是唯一碰机器人的东西。** 十五个舵机和 IMU 板共享一条串行总线，50 Hz 控制循环拥有它。客户端发*意图*——「以这个速度走」、「看那里」、「站起来」——而 `robotd` 内部的安全层决定什么实际可执行。系统里没有别的东西能命令一个电机（[`robotd-design.md`](robotd-design.md)）。

**它们中的三个挺得过一个死掉的 `robotd`。** `configd`、`updaterd` 和 `btd` 对它没有 systemd 依赖、没有 ML 运行时、没有媒体栈，因为它们是恢复路径：一台其控制循环起不来的机器人，正是某人需要重新配置、更新或回滚的机器人。这也是配置住在 `configd` 而非 `robotd` 的原因（§1.1）。`mediad` 和 `padd` 依赖于管线。三个都是可替换的而不碰机器人行为，且三个都被每天演练，所以一个 App 要用的 API 不会悄悄烂掉。`tofd` 是异类：它拥有一个传感器、发布帧、什么都不读（§1）。

**发布是交换，不是打补丁。** 一个构建作为整个目录落在 `/opt/robot/daemon/releases/<version>/` 下；`updaterd` 校验它的签名、移动 `current` 符号链接、重启各 unit，然后问 `robotd` 是否健康。如果不，它自己把旧发布放回。一个闯过那个的崩溃循环被一个启动计数器抓住（[`updater-design.md`](updater-design.md)）。

| 服务 | 拥有 | 监听 | 向外触达 |
|---|---|---|---|
| `robotd` | 电机控制、感知、策略、安全、`robot.health` | `/run/robotd.sock` | Dynamixel 总线 |
| `configd` | wifi、机器人身份和名字、配对 PIN、手柄配对、重启 | `/run/configd.sock` | D-Bus 上的 BlueZ 和 NetworkManager |
| `updaterd` | 发布：校验、安装、交换、健康门控、回滚 | `/run/updaterd.sock` | GitHub 发布、`systemctl`、`robotd` |
| `btd` | 无——API 子集的 BLE 传输 | 一个 BLE GATT 服务 | `robotd`、`configd`、`updaterd`——不是 `padd` 或 `tofd`，这么窄的无线电载不动它们的流 |
| `padd` | 无——游戏手柄传输；服务一个原始输入 tap | `/run/padd/pad.sock`（仅 `pad.input`） | `/run/robotd.sock` |
| `netpadd` | 无——局域网 UDP 上的游戏手柄传输，替代 `padd`（[`udp-pad.md`](../robot/udp-pad.md)） | UDP `[netpad] port` | `/run/robotd.sock` |
| `mediad` | 摄像头和音频管线；机器人的任何东西都不归它——WebRTC 传输和远程前门（§5.2） | TCP：`:8080` 上的控制台和 PNG `GET /frame`、`:8443` 上的信令；以及一个它自己的 unix 套接字 `/run/mediad/media.sock`，给本地录制器或感知进程服务 `media.frame`——也服务 `robotctl monitor` 的摄像头块，它在打开时每秒要两次、关闭时一次都不要。一帧原始约 1.8 MiB，所以它刻意不走 WebRTC 控制通道 | `robotd`、`configd`、`updaterd` |
| `tofd` | 头部的 ToF 传感器：一个它发布、没别人读的 8×8 深度矩阵 | `/run/tofd/tof.sock`（`tof.stream`） | HAT 的 I²C 总线，或 beta 板上的 SPI（`tof::link`） |
| `robotctl` | 无——CLI，且是必须在一台坏机器人上也能工作的工具 | — | 上面每个套接字 |

状态住在哪，什么挺过一次更新：

| | |
|---|---|
| `/etc/robot/robotd.toml`、`updater.toml` | 每板配置；安装器写一次、永不覆盖。`robotd.toml` 由 `robotd` 读，而——仅 `[media]`，摄像头推流什么——由 `mediad` 读，所以那里的一次更改重启 `mediad` 而非 `robotd` |
| `/var/lib/robot/config/config.json` | 机器人名字和配对 PIN——一个文件加 `flock`，归 `configd`（§3.1） |
| `/var/lib/robot/vetbook.json` | 兽医手册——机器人的终身记录，归 `robotd`（`robotd/src/vetbook.rs`） |
| NetworkManager profiles | wifi 凭据；我们从不存它们（§3） |
| `/opt/robot/daemon/releases/<ver>/` | 二进制、策略和随附默认值——原子替换 |
| `/opt/robot/daemon/current` | 说哪个发布在线的符号链接 |
| `/run/<service>/identity.json` | 每个守护进程实际在跑什么，启动时发布 |

`releases/<ver>/` 之外的一切都挺过更新和回滚。那是全部规则，也是每板配置不随发布发布的原因。

一次更改如何端到端到达机器人：

```text
  推一个分支 ──► CI 构建并签名一个发布 ──► robotctl update apply
                                                            │
                                                            ▼
                                          updaterd：校验签名、解包、
                                          移动 `current`、重启各 unit
                                                            │
                                                            ▼
                                          健康门控：问 robot.health
                                            ├─ 健康  ──► 保留它
                                            └─ 不健康 ──► 把旧的放回
```

本文档其余部分是推理：服务拆分（§1）、服务如何交谈（§2）、谁拥有哪个状态（§3）、API 及其传输（§4）、远程访问（§5），以及安全权威坐哪（§6）。

## 1. 服务

`systemd` 是监督者：生命周期、崩溃重启、顺序、看门狗。

| 服务 | 拥有 | 备注 |
|---|---|---|
| `robotd` | 电机控制、运动学、里程计、步态策略、传感器循环、安全 | RT 级核心；对任何可能伤害机器人的东西权威。里程计是循环里的一个 struct |
| `configd` | wifi、机器人身份和名字、配对 PIN、手柄配对、重启 | 需要 root 和 BlueZ，而 `padd` 刻意是一个无特权客户端（§4.1） |
| `tofd` | 头部 ToF 传感器：HAT I²C 总线上的 8×8 深度矩阵 | 感知，所以按下面的原因与 `robotd` 分开。拥有一个传感器并发布帧；什么都不读。一块没装传感器的板子照样跑它并说明 |
| `updaterd` | 更新引擎 | 见 `updater-design.md` |

把 `mediad` 从 `robotd` 分开是刻意的：媒体/感知崩溃绝不能带走电机控制。`tofd` 是把同一条规则用于一个更小的传感器，而细节说明了理由：让 VL53L5/8CX 起来要在 I²C 上传 ~90 KB 固件、花几秒，总线与音频编解码器共享，而大多数鸭子根本没装传感器——对那个的重试循环不属于拥有电机的进程。控制循环里没有任何东西读深度，所以把它移出去什么都不损失。它刻意*不是* `mediad` 的一部分：深度是总线上的传感器，不是媒体管线，而且它在有摄像头可标注之前很久就有用。

消费者像到达手柄原始流那样到达它——在拥有它的守护进程自己的套接字上的一个订阅（`tof.stream`），从不经 `robotd`。把一帧重投影进机器人自己的坐标系，意味着经 `kinematics` crate 的头部 FK 与 `robot.state` 的关节状态结合；`tofd` 发布传感器的视图，不假装它能算它算不了的几何。

### 1.1 不变量

1. **`btd`、`configd` 和 `updaterd` 挺得过一个死掉的 `robotd`。** 它们是恢复路径；它们必须恰好在那东西坏了的局面里工作。对 `robotd` 无 systemd 依赖、所有 IPC 可选且有超时上限、最小依赖面（无 ML 运行时、无媒体栈）。详见 `updater-design.md` §4.1。

   `configd` 在这里有一个具体原因而非对称：provisioning wifi 恰是某人在机器人坏掉时需要的东西，所以把配置放进 `robotd` 会让它在那唯一要紧的情形里不可达。
2. **`robotd` 对安全权威。** 没有远程或本地客户端能绕过跌倒检测、关节/温度限制或安全姿态逻辑。客户端发*意图*；`robotd` 决定什么可执行。
3. **`robotd` 的控制循环永不阻塞在另一个服务上。** 所有跨服务读取都是 last-value-wins 缓存，从不同步 RPC（§2.4）。
4. **每份状态一个写入者。** 每个值恰好有一个拥有服务；其他人读或订阅。

## 2. 服务间通信

### 2.1 控制面 vs 数据面

两种要求不同的流量。把它们混为一谈是这里的经典错误。

| | 控制面 | 数据面 |
|---|---|---|
| 内容 | 命令、配置、状态、感知事件 | 视频/音频帧 |
| 大小/速率 | 几十字节，≤100 Hz | 640×480 RGB @30 fps 约 27 MB/s |
| 机制 | unix 套接字 RPC | **从不跨套接字** |

### 2.2 控制面：unix 套接字上的 JSON-RPC 2.0

- 每个服务拥有**一个 unix 套接字**。客户端直连。N=4 时没有理由要代理——总线是另一个可能失败的组件，且它违背不变量 (1)。
- **线格式：JSON-RPC 2.0，一行一个对象（NDJSON）。** 一个标准协议而非自造：标准请求/响应关联、标准错误对象、标准**通知**——它们恰好是推送进度和事件流的正确形状。帧是 `tokio_util::codec::LinesCodec`；消息类型是普通 `serde` 结构体。
- **处处异步带超时、没有例外。** 任何对端都可能死。一个关闭或沉默的套接字是正常的、预期的答案。
- 订阅是开放连接上的通知流。

**衡量过的替代**（唯一依赖数、ARM-Linux 目标）：

| 选项 | 依赖 | 为何不 |
|---|---|---|
| **JSON-RPC/NDJSON + tokio** | **30** | 选中 |
| 仅 `jsonrpsee-types`（我们的传输） | 36 | 合理；谢绝——用冻结规范的代码换一个 `0.x` 依赖 |
| `varlink` | 24 | 精神接近；更不熟，相对 JSON-RPC 收获甚微 |
| `zbus`（D-Bus，p2p+阻塞） | 66 | 见下 |
| UDS 上的 `axum` | 66 | 可行；见下「HTTP/WS」 |
| `tarpc` | 71 | Rust↔Rust 顺手，但不可人读、服务器推送别扭 |
| `tonic`（gRPC） | 81 | 为少数几个方法付 `.proto` + 代码生成开销 |
| `jsonrpsee-server` | 112 | **不能服务 unix 套接字**——只有 HTTP/WS 传输；`jsonrpsee-ipc` 从未实现 |

依赖计数是为参考记录，不是决定因素。

**为什么 unix 套接字而非 localhost HTTP/WS。** 功能上几乎相同；差异在访问控制和失败模式：

- **文件系统权限是免费授权。** 一个 mode 0660、专用组的套接字只被允许的进程到达。一个 TCP 端口被机器上每个进程和用户到达，所以要建一个认证层才能回到同等。
- **`SO_PEERCRED`** 产出调用者的 uid/gid/pid，用于*两者*——审计日志（「谁触发了这次回滚」是支持问的第一件事）和**执行**。两层，因为它们回答不同问题：
  - 套接字的组（mode 0660）决定谁可以**跟**守护进程说话；
  - `allow_uids`/`allow_gids` 决定谁可以**改变机器人**——仅变更类调用。守护进程运行所使的 uid 总被允许（它无论如何都能替换守护进程）；其他人都需要列出，一个未知对端被拒绝。
  只读调用刻意不设门：支持必须能检查一台它无权更改的机器人。单靠组成员说「可以替换固件」对一台 BLE 面向服务是客户端的设备太粗。
- **错误接口的 bug 类停止存在。** 因拼写错误、配置或一个「让我从笔记本跑通」的补丁而绑定 `0.0.0.0`，会把*固件更新控制*暴露给网络。在 unix 套接字上那个错误无法表达。权重最重——不是今天的威胁模型，而是失败模式。
- 与计划中的 **SDK** 相关：如果第三方或用户代码在板上运行，一个 localhost 端口对它开放；一个组拥有的套接字不。

**为什么不用 HTTP/WS 作控制面**（与传输无关——`axum` 服务 UDS 没问题）：协议需要服务器→客户端推送进度。在 HTTP 上那意味着调用用 POST *加*通知用 WebSocket/SSE——两个机制，而 `curl` 消费不了流式那半，所以可调试性的收益只覆盖请求/响应。全走一个 WebSocket 恢复一个机制，但要一次握手才到帧化的 JSON、又失去 `curl`。在持久 NDJSON 连接上，调用和通知是一个机制、无握手：**更少的概念，这才是真正的目标。**

**未来选项，如果诊断想要 `curl`-able：** 同一 unix 套接字上的一个小*只读* HTTP 端点（`GET /status`、`GET /log`），给出 `curl --unix-socket … http://x/status` 而无需把控制操作移到 HTTP 上或复制流式路径。诊断和控制要求不同；分开它们服务两者。

**为什么不用 D-Bus：** BlueZ（经 `bluer`）反正已经拉它进来，所以它在机器上，且 `zbus` 支持无总线对等。但同样的消息类型还必须经 **BLE 和 WebRTC/WebSocket**（§4.1、§5.2）走，那里普通 serde 结构体管用、D-Bus 类型不管。一份定义、多种传输是目标，JSON 是让它免费的东西。我们只在操作系统要求的地方用 D-Bus（BlueZ、NetworkManager）。

**重访触发：** 如果 `btd` 反正要为 BlueZ 深投 D-Bus，把更新接口也经 `zbus` 暴露对*`btd`* 几乎免费，还会买来调试用的 `busctl` 自省。便宜可改——类型还在、只有帧移动。

### 2.3 等待处异步，计算处同步

异步（tokio）用在一个服务真的等待的地方：长操作运行期间服务 IPC、给一个对端查询或子进程超时、取消进行中的工作。

CPU 密集和长时间文件系统工作保持**同步**，异步调用者把它交给 `spawn_blocking`。在更新器里那具体是：工件上的 SHA-256、minisign 流校验、`zstd`+`tar` 解包，以及解包树的递归删除。在 Pi 上这些跑几秒；留在异步 worker 上会卡住本该在更新期间继续应答 `status`/`subscribe` 的 IPC 任务。

真正快的文件系统操作——一个符号链接 `rename`、一个 fsync、一次小追加——直接调用。把它们派到线程池花的比省的多。

### 2.4 数据面：特征，不是帧

`robotd` 不需要摄像头帧——它需要*派生特征*（「球在 (x,y)」、「检测到人」、「响亮的声音」）。几十字节在 10–30 Hz，套接字上微不足道。

**原则：把感知放在传感器旁边。** `mediad` 拥有摄像头、跑推理、发布特征。把帧送给 `robotd` 好让它跑自己的视觉，会浪费板子大部分内存带宽。

**在控制循环里：** `robotd` 订阅一次并读一个本地缓存的*最新*快照——非阻塞、last-value-wins。一个卡住的 `mediad` 那时降级感知、而非给电机控制加抖动。

**如果帧必须跨进程边界**（最后手段）：共享内存（shm/dmabuf 环形缓冲），套接字只带「第 N 帧就绪于偏移 X」。libcamera 提供 dmabuf，所以这能零拷贝。偏好特征-而非-帧、避免需要这个。

## 3. 状态拥有

三个不同类别；更新/回滚含义见 `updater-design.md` §5.7。

| 状态 | 拥有者 | 机制 |
|---|---|---|
| Wifi 凭据 | **NetworkManager** | 我们从不存。`configd` 经 D-Bus 驱动 NM；NM 以 root-only 持久化 profiles 并自己重连。 |
| 机器人身份、用户偏好、可调项 | **配置仓库**（§3.1） | 文件 + `flock` + `rename(2)`，归 `configd` |
| 标定、学得状态、生成的每设备资产 | 拥有服务 | 在发布目录外；挺过更新*和*回滚 |
| 随附默认值、二进制、策略包 | 更新系统 | 在 `releases/<ver>/` 下，原子交换 |

让 NetworkManager 拥有 wifi 凭据是更少的代码、更好的安全、且少一样要迁移的东西。

**一块板子到达时并没有 NetworkManager**，这一行最初假设有。Armbian 的无头镜像跑 netplan + `systemd-networkd` + `wpa_supplicant`，而 netplan 是一个配置*生成器*：它没有扫描 API，且 `netplan apply` 报告「config applied」而非关联是否成功。那两样正是一部 provisioning 机器人的手机最需要的——「给我看网络」和「那个密码错了」——所以决定成立，`scripts/migrate-network.sh` 把板子移到 NM 一次。推理和板上测了什么，在 [`app-path-design.md`](app-path-design.md) §2。

### 3.1 配置仓库

一个普通文件加一个小共享 crate——**刻意不是服务**：

- 写序列化用 `flock`；原子性用写临时文件 + `rename(2)`。
- 变更通知用 `inotify`。
- 没有单点故障，任何服务挂掉时都可读，更新器从不碰它（`updater-design.md` §5.7）。

实现在 `configd/src/store.rs`，持有机器人的名字和它的蓝牙配对 PIN。`inotify` **还**不在那里，刻意地：当*第二个*进程读该文件时它挣得自己的位置，而今天 `configd` 是唯一一个。监视一个你是唯一写入者的文件是仪式。

配置**必须**在 `robotd` 死掉时可到达——wifi provisioning 恰是客户端在东西坏掉时需要的——这就是它不能住在 `robotd` 的原因。

**配置是状态，不是动作。** 「连这个 wifi」、「重启」、「应用更新」、「选模型」是动作，作为 RPC 派给拥有服务。

### 3.2 面部 LED

beta 板的面部在 GPIO 扩展器上带十二个 LED，它的设备树在 `/sys/class/leds` 下把它们命名为 `face:<place>:<colour>`。一个 LED 显示一份状态，所以它遵循不变量 4：**每个 LED 有一个写入者，即拥有它所显示内容的守护进程。** Zero 3W 一个都没有，而每个拥有者在一块没有它的 LED 的板上什么都不做。

| LED | sysfs | 拥有者 | 显示 |
|---|---|---|---|
| 手电筒 | `rgb:{red,green,blue}` | `robotd` | `robot.flashlight` 最后要求的，七色之一。手柄的 Home 键切换它。 |
| 摄像头 | `cam:red` | `mediad` | 画面离开机器人时亮：一个正被编码的 WebRTC 对端，或一个运行中的 `media.stream`（§7）。不是留在机器人上的 `media.frame` 快照。 |
| 状态 | `gr2:{green,red}` | `robotd` | `robot.health`：绿健康；第一个节拍前闪绿；闪红降级（无舵机电源、一个舵机被拔——板的错、不是发布的）；红不健康。 |
| 网络 | `gb:{green,blue}` | `configd` | 从局域网外可达时蓝（中继带着一个活心跳注册）；否则 wifi 上绿、加入时闪绿、没有时灭。 |
| 电池 | `gr1:{green,red}`、`green2`、`green1`（下到上） | `robotd` | 从 `gr1` 向上填的三档量表：70% 以上三绿、40% 以上两绿、15% 以上一绿；然后 `gr1` 红、5% 及以下闪。每档 3% 迟滞。第一次读数前灭。 |

网络 LED 读一个它不拥有的事实：`mediad` 的中继是否注册，来自 `mediad` 为读者发布的文件（`/run/mediad/remote.json`）。它仍有一个写入者，因为两个守护进程的绿和蓝会同时显示两者。

每个拥有者只在变化时写，这让 `robotctl led` 在拥有者下次有新东西要说之前可作台架覆盖；停止时关掉它的 LED；unit 里有一个 `ExecStopPost` 在它崩溃时做同样的事。各 unit 把 `/sys/devices/platform/face-leds` 交回守护进程，因为 `ProtectKernelTunables` 让 `/sys` 只读。[`duck_ipc_proto::led`](../../duck-ipc-proto/src/led.rs) 是共享写入者和名字。

## 4. 机器人 API

### 4.1 一份定义，多种传输

`btd` **什么都不拥有**。BLE 是几个前门之一。如果配置或 provisioning 住在 `btd`，其他服务会依赖它，而一个 SDK 会荒谬地必须走 BLE。

```
        ┌──────── 一份 API 定义（共享 crate：类型 + 操作）
        │
   ┌────┴─────┬────────────┬──────────────┬────────────────┐
  BLE       unix 套接字   rendezvous    WebRTC 数据通道
 (btd)      robotctl、    控制通道      遥在、
  子集     板上 SDK      agents/LLM    全保真
```

每个传输是同一 API 上的薄适配器。BLE 暴露一个**子集**（provisioning、状态、更新触发/进度）——它对完整面太慢太受限，负载从不经它。

### 4.2 横切规则

- **每传输授权。** BLE 意味着物理在场 + 配对；网络传输要 token。同一 API、不同 authz——从一开始决定检查住哪。
- **API 版本握手。** SDK 和守护进程版本*会*漂移。一个整数，不匹配时带清晰消息拒绝（与 `model_api` 同法）。
- **意图，不是电机写。** 见 §6。

## 5. 远程访问

### 5.1 要求

所有机器人和媒体数据必须经一个 **WebRTC** 连接可达，以支持 (a) 遥在和 (b) 一个观察并控制机器人的服务器端程序（例如 LLM）。后者必须*容易*。

### 5.2 WebRTC 会话

一个 PeerConnection 承载一切：

```
对端（浏览器 / 手机 / 服务器）
   ├── 视频轨 ── 摄像头
   ├── 音频轨 ── 麦克风 + 扬声器（遥在双向）
   ├── 数据通道 "control"   可靠、有序      → 机器人 API（§4）
   └── 数据通道 "teleop"    不可靠、无序    → 输入 + 高速遥测
```

两条数据通道，镜像 §2.1：遥操作输入和遥测走**不可靠**（`maxRetransmits: 0`），因为一条重传的、80 ms 旧的摇杆命令比没用更糟——总取最新的。

**`mediad` 拥有 PeerConnection。** 一个 PC 无法跨进程拆分（轨和数据通道共享一个 DTLS/SCTP 关联），且它需要编码媒体，所以它和 `mediad` 在一起，后者把 `control` 消息经它们的 unix 套接字代理给拥有服务。因此 `mediad` 是**远程网关**。

隔离代价可接受：没有媒体一个遥在会话就毫无价值，所以共处不损失一个拆分能保留的任何东西。本地恢复经 BLE / `robotctl` 保持独立（不变量 1）。

### 5.3 服务器端 agent：别逼它们走 WebRTC

对一个 LLM 驱动的控制器，WebRTC 是*更难*的路。一个 agent 不想要一条 30 fps H.264 轨去解码——它要每一两秒一帧加一个状态块。先要求 ICE/DTLS/SDP 和一条解码管线是个差交易。

| 消费者 | 控制 | 媒体 |
|---|---|---|
| 遥在（人） | WebRTC 数据通道 | 轨，低延迟 |
| 服务器端 agent / LLM | **rendezvous 控制通道**——HTTP/SSE 上的 JSON-RPC，无 WebRTC | WebRTC 轨；长跑程序用 `media.stream` |
| 板上 SDK、`robotctl` | unix 套接字 | 快照 API |
| App | BLE + WebRTC | 按需 |

它们背后同一个 API。「在一个服务器上跑一个控制机器人的 LLM」变成：登录、经 rendezvous 发意图、只在想要时取视频。控制通道无需 ICE、DTLS 或 TURN 就从数据中心到达机器人，这正是让它真正容易的东西；[`remote-access-design.md`](remote-access-design.md) §3.8 拥有它，[`faq.md`](../faq.md) 说选哪条媒体路径。

还要注意 LLM 延迟（几百 ms 到秒）意味着 agent 是**高层**控制器：「去厨房」、「看那个人」。反应式控制留在本地 `robotd`。无论传输如何，这都是正确的拆分。

### 5.4 基础设施现实检查

「机器人有自己的 wifi」**不**等于「从互联网可达」。远程 WebRTC 需要：

- 一条**信令**路径（SDP/ICE 交换）、
- **STUN**，以及 **TURN** 作为对称 NAT 的中继后备——真基础设施、真带宽成本。

这与更新设计的「零后端」前提矛盾。**仅局域网遥在完全避开它；互联网遥在则不。** 开放问题（§9）。

### 5.5 实现注记

库的选择取决于硬件编码：如果要 V4L2 M2M 硬件 H.264，GStreamer `webrtcbin` 更务实；`webrtc-rs` 是纯 Rust、更轻于推理，但留给我们建管线。这实质地塑造 `mediad`——早决定。

遥在驾驶的延迟预算：目标 **<200 ms 玻璃到玻璃**。意味着低延迟编码器设置、无 B 帧、帧内刷新而非大关键帧。

## 6. 安全与权威

在有损链路上远程控制一台走路的机器人。这些设计进去比事后改造便宜得多。

- **Deadman / 心跳。** 如果命令停止到达或 RTT 尖峰超过阈值，`robotd` 自己停住机器人。不可谈判：网络会分区、LLM 会在推理中途停、笔记本会睡。
- **意图，不是电机写。** 远程客户端发速度、注视目标、「坐」——从不原始关节命令。`robotd` 保持对跌倒检测、关节/温度限制和安全姿态的权威。一个困惑的 agent 绝不能能命令机器人会执行进墙里的东西。
- **显式权威仲裁。** 物理控制器、App、远程对端和自主行为层都想要控制。定义的优先级和交接，不是 last-writer-wins。本地/物理应能抢占远程。
- **会话限制。** v1：一次一个媒体会话，加 M 个纯控制客户端。多对端视频（simulcast、编码一次发多个）推迟。

## 7. 隐私

它是一台在某人家里摄像头和麦克风。

- **显式同意**开始一个远程会话（每会话，或一个用户可撤销的清晰持久选择加入）。
- **推流激活时机器人上可见的指示器。** 在 beta 板上，摄像头 LED（§3.2）。
- DTLS-SRTP 让媒体端到端加密**甚至经 TURN 中继**——值得向客户端说清楚。
- BLE provisioning 写携带 wifi 凭据：那个特征必须已配对 + 已加密。

## 8. 可观测性：日志和版本

横切的，因为一台在某人家里机器人不能靠接调试器来调试。支持能要的东西必须已经在机器人上。

部署细节——journald drop-in、安装步骤、校验命令——在 [`../deploy/README.md`](../../deploy/README.md)。这一节是每个服务必须满足的契约。

### 8.1 身份与启动日志

每个守护进程在启动时、于它能失败之前，以 `warn` 记录一行身份：版本、git 修订版，以及进程从哪个发布目录启动。这一行挺过任何日志级别，是任何诊断的锚。

### 8.2 版本：一个版本，四处可恢复

`robotctl version` 报告每个守护进程正在*运行*什么对已*安装*什么，并点名不一致：

- `updaterd` 落后于已安装发布 → 短暂预期，且是没有东西自我修复的那个漂移：后继报告它而非重启自己，所以如果它持续、安排的重启没发生；
- `robotd` 落后于它 → *不*预期，因为它在 `on_apply` 的重启集里，所以重启没生效。

那是不同诊断、绝不可共享一条消息。`--json` 给同样内容用于支持包，命令在 `updaterd` **挂掉**时也能用——把它报告为一行而非退出，因为那正是有人够它的时候。

四处独立可恢复版本，所以丢一个可存活：启动日志行；IPC 上的 `robotctl version`；每个二进制上的 `--version`；每个发布目录里的 `version.toml`（加 `robotctl update list`，它显示每个已安装发布从哪个修订版构建）。

`revision` 从 `DUCK_REVISION` 编译进来——CI 设、本地没有，那里二进制诚实报 `rev unknown, not a CI build`。编译时读、绝不在运行时从 git 读：一台发布的机器人没有仓库。它比看起来重要：一旦分支安装落地（路线图 M2），几个构建共享一个版本号，修订版是唯一区分它们的东西。

### 8.4 健康是一个问题，所以它是一条命令

`robotctl health` 在单个答案里报告来自 `robotd` 的硬件和来自 `updaterd` 的软件。那不是方便：「这台机器人怎么了」直到*它被回答之后*才分成硬件和软件，而一台一小时前回退了发布的机器人，在两者同屏之前看起来和一台舵机没电的机器人一模一样。拆分它会让调用者在知道哪半有错之前先选一半。

它**在机器人不健康或不可达时非零退出**，所以它能门控一个脚本——任何建在其上的东西都依赖的契约。没有别的影响退出码：一块亏电、一个热电机、一个被固定的组件被报告、不被判定。一个发布绝不可因它落地的板子的状态而被回滚。

`--json` 携带同样内容用于支持包。

## 9. 开放问题

1. **v1 互联网可达遥在，还是仅局域网？** 大的那个：无后端与运营信令 + TURN 的差别（§5.4）。
2. **SDK 是团队内部还是发布给最终用户？** 决定 API 兼容承诺有多硬（§4.2）。
3. **权威优先级**当 App、远程对端和自主行为不一致时——即使一个粗糙固定顺序，但决定而非涌现（§6）。
4. **感知在 `mediad` 还是它自己的 `perceptiond`？** 打包让推理挨着摄像头、更简单；拆分意味着一次感知崩溃不杀视频流。取决于视觉变多重。
5. **行为/大脑层**（驱力、心情、习惯）：`robotd` 的一部分，还是它自己的服务和更新通道？它学得的状态无论如何都是 `updater-design.md` §5.7 材料。
6. **BLE 上的配对撤销。** 没有东西解除一部手机的配对；`bluetoothctl untrust` 是手动逃生。需要 API 和一条谁能调它的规则（[`app-path-design.md`](app-path-design.md) §5）。
7. **每设备 provisioning 状态**——每机器人配对 PIN，现在没别的。序列号是另一个主张者、不再需要槽位：它熔进 SoC（`updater-design.md` §5.6，[`app-path-design.md`](app-path-design.md) §8.2 说它在每块板上从哪读）。PIN 不能共享身份，那曾是计划：身份发布在广播里，所以任何从它派生的东西都是公开的。一个秘密仍须在制造时生成、记录和打印。

## 10. 构建顺序

`updaterd` **先**建，然后用来发布本架构其余部分的每个后续迭代。这在失败还免费（没有客户端、没有有价值的东西可破坏）时前置更新系统风险，且意味着更新路径在机器人发布前被演练几百次。

这样做时要尊重的后果：

- `updaterd` 对一个到 `robotd` 的**接口**（健康探测、可安全重启）构建、而非一个实现——初始打桩，那也是让它可测的东西。
- 早期健康探测会弱（「进程活着」）。自动回滚信心随 `robotd` 成熟而增长；先被测的是*机制*。
- **整个早期开发期间保持一条手动恢复路径（SSH / 重刷）。** 更新器既未验证又快速变化，且它随它更新的工件发布——别让它成为唯一的回头路。
- 无法事后改造的 schema 字段（`min_supported`、`schema_version`、`model_api`）从第一个发布就在，即使不用。
