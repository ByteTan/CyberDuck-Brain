# WebRTC 客户端：从一个测试页面到机器人的控制台

状态：已落地 · 日期：2026-08-25 · 负责人：pierre

`mediad/webclient/index.html` 证明了传输层。这是把它变成一个人真正使用的东西：由机器人
来提供页面而不是 `python3`，通过 `btd` 已经在广播的地址被找到，并实际使用 `route.rs` 真正
允许的控制表面。

[`remote-webrtc.md`](remote-webrtc.md) 的姊妹篇，后者拥有传输层——信令、会话模型、授权，
以及一个 peer 可以调用什么。两者接触之处，以那页为所有者，本页指向它。

**四项改动都已就位。** 本页写于它们的第一行代码之前，所以这些决定是可以争辩的，而不是由
diff 隐含的；之所以保留它，是因为各替代方案正是值得反复重读的部分。代码与本页可能漂移的
地方，以代码为准：`mediad/src/web.rs` 提供页面，`mediad/src/producer.rs` 填充 `meta`，
`duckctl` 的 `ip` 和 `open` 找到机器人，而 `mediad/webclient/index.html` 是控制台。§7 说明
还剩什么。

## 0. 它原来的问题

就其原本用途而言，问题不大。它回答了“浏览器能否拿到视频和一个 datachannel”，答案是能。
作为*一个客户端*，它有六个问题：

| | |
|---|---|
| 它需要 `python3 -m http.server` | 第二个工具和第二个终端，而且页面从笔记本提供、去和机器人通话 |
| URL 要手打 | `ws://radxa-zero3.local:8443`——而 `radxa-zero3` 是**每块**从同一镜像烧录的板子上的主机名（`configd/src/main.rs` 在回退到它时这么写），所以同一网络上的两台机器人会冲突 |
| 它的注释块大多是警告 | `file://` 和 Private Network Access，http 而非 https——一个已经不得不修正两次的头（`7f52a34`） |
| 它演练的是协议，而不是机器人 | `route.rs` 允许 move、head、look、pose、mouth、do、sound、enable、init、relax、stop、subscribe、`tof.stream`、`pad.input`。页面只提供 `robot.health` 和一个 JSON 文本框 |
| 它哪里都没发布 | 没有 `--include` 指名它，所以现场的机器人没有客户端 |
| 它说不出自己连到了哪个机器人 | producer 的 `meta` 未设置，所以 `list` 只返回一个 id，别无其它 |

其中每一条都是一个人与一台可用机器人之间的一道坎，而且没有一条是关于 WebRTC 的。

## 1. `mediad` 提供页面

**已落地**——`mediad/src/web.rs`，`--web-port`，默认 8080。

`mediad` 里一个 HTTP 监听器，一条路由，返回页面。`http://<robot>:8080/`，此外无需运行
任何东西。

这同时删除了四个问题，而非一个：

- **不再需要 `python3`。** 指令变成了一个地址。
- **没有要打的 URL。** 页面把它的信令目标默认为 `ws://${location.hostname}:8443`——它是由
  机器人提供的，所以它知道自己在和哪个机器人说话。
- **Private Network Access 不再适用。** Chrome 会阻止来自*公共或不透明*源的、指向私有地址的
  请求。一个由 `192.168.x` 提供的页面拥有私有源，所以那条弄坏 `file://` 的检查根本走不到。
  头部的警告块消失了，因为它所警告的失败不可能发生。
- **单一版本。** 页面和二进制一起发布（§1.2），所以来自某个 checkout 的客户端再也无法指向
  来自某个 release 的机器人。

### 1.1 用哪个 HTTP 服务器

**`axum`。已决定。** 它已经在 `Cargo.lock` 里——`updater` 把它用作其测试镜像的
dev-dependency——所以这个 crate 对本工具链和交叉构建来说是已知良好的。

替代方案是一个手写的 HTTP/1.1 响应器：它只通过一种方法提供一个文件，所以大约六十行。
六十行手写的、绑定到 `0.0.0.0` 的请求解析，是暴露给网络上所有人的解析器，写它只是为了
避开一个构建本就已解析的依赖——而 `axum` 底下的 `hyper` 是这门语言里被最多人读过的那份
解析器实现。

`mediad.service` 里的 `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6` 已允许该监听器；
unit 里什么都不用改。

### 1.2 页面是内嵌的，不是安装的

`include_str!("../webclient/index.html")`，从内存提供。

替代方案——把它安装到 `/opt/robot/daemon/current/webclient/` 下并在请求时读取——要在*三处*
（`_build-release.yml`、`dev.yml`、`scripts/dev-push.sh`）各加一行 `--include`，而 `xtask` 的
打包绊线正是为了保持这些同步而存在，而那恰恰是以前漂移过的清单。它还让一次文件系统读取
躲在一个运行着 `ProtectSystem=strict` 的 unit 的网络请求后面，并把“这台机器人在提供哪个
页面”变成一个有两个答案的问题。

内嵌的代价是改一个样式表就要重新构建。对一个作为守护进程界面一部分的页面来说，这是正确
的取舍。

### 1.3 两个端口，且没有人需要知道有两个

`webrtcsink` 拥有 8443 上的监听器（`run-si…`），8080 是页面。分开的原因有两半，而第二半正是
值得现在就写下来的：

- 页面要能在机器人出于任何原因都还没完全起来时被提供；WebRTC 栈则只有在摄像头和编码器
  可用时才能被提供。合并在一个端口上，会让“页面出来了”和“信令起来了”这两件不同的事变成
  同一件事。
- **两个端口可能产生的那个失败，要用话说出来。** 如果 8080 有应答而 8443 没有——最可能是
  中间隔着防火墙——页面必须说*页面来自这台机器人，但它的信令端口没有应答*，而不是
  `websocket error`。这是第二个端口唯一能触达一个人的途径，而且应该以诊断的形式触达。

单端口变体是我们自己运行信令服务器——上游把它作为库与插件一并发布——并把 `webrtcsink` 的
signaller 指向 `ws://127.0.0.1:8080/ws`。这样一个 `axum` 服务器就在一个源上同时提供页面和
协议。工作量更大，而且还要多维护一份协议版本、与我们发布的 `.so` 保持同步，所以不在第一项
改动里做。

**但这是它的归宿，理由如下。** 浏览器不会给一个通过明文 http 提供到私有地址的页面以麦克风，
依浏览器而定，手柄也没有——那些是 secure-context API，而 `http://192.168.1.42` 不是安全
上下文（`http://localhost` 是，这正是至今还没人撞上的原因）。双向音频在 `remote-webrtc.md`
§2。机器人将需要提供 TLS，而 `webrtcsink` 内置的服务器无从配置证书，`axum` 服务器则提供
普通的那一种。所以顺序是：现在两个端口，想要音频或浏览器手柄时上我们自己的信令服务器，
TLS 在同一天上。

值得现在就写下来，而不是在接麦克风时才撞见。

## 2. 找到机器人：两条命令，其中一条已经被手写过了

**已落地**——`duckctl ip` 和 `duckctl open`，先广播、其后是 `net.status`。

`btd` 把机器人的 IPv4 放进它 company id `0xFFFF` 下的广播里，而 `duckctl` 已经在解析它——
`Address::At`、`Unassigned`、`Unsaid`，三个答案而非两个，`scan` 今天就在打印它。所以工作
是一条命令，而不是一个机制。

### 2.1 `duckctl ip`

机器人的地址写到 stdout 且别无其它，所以 `ssh microduck@$(duckctl ip)` 能工作——这是该工具
已经保持的分工，诊断走 stderr、数据走 stdout。

**这不是本仓库的新想法；它是一个已经被写过一次、而且写得很糟的想法。** `scripts/dev-push.sh`
恰好需要这个并手写了它：`resolve_board()` 调用 `duckctl wifi status`，把 JSON 经一个内嵌在
shell 脚本里的六行 Python 程序拉出 `result.ip4`。那就是这条命令，只是没有家。

读广播而不是调用 `net.status` 在三点上更好，这三点都体现在 `dev-push.sh` 不得不绕开的
代码里：

- **无需连接，所以没有 bond、没有 PIN。** `resolve_board` 带了一整个针对“机器人拒绝了
  `net.status`——最常见是 PIN 错了”的失败分支。广播读取无法被拒绝，所以那个分支不复存在。
- **几秒而不是几十秒。** `dev-push.sh` 按机器人缓存地址，正是因为“BLE 发现要花十到二十秒”；
  一次在第一个匹配广播处停下的扫描大约一秒，因为 `duckctl` 已经会轮询直到有东西出现，
  而不是睡满 `SCAN_TIME`。
- **它不是陈旧的。** `btd` 的 `reconcile_advertisement` 每 `ADV_POLL`（5 秒）重读一次
  `net.status`，答案变化时重新广播，所以广播*就是*带着五秒滞后的 `net.status`——远在新租约
  已经弄断 ssh 的那个窗口之内。

**有一个 fallback，它不是可选的。** 一台已与这台 Mac bond 的机器人常常会停止对它广播服务——
`duckctl` 自己的扫描分层正是为此而存在——所以当看不到广播时，`ip` 连接并询问 `net.status`，
这正是 `dev-push.sh` 今天所做的。先廉价读取，再调用。没有这个 fallback，这条命令恰恰会在
最常使用它的那些笔记本上失败。

三态的 `Address` 已经带着正确的失败文案，而这里正是它回本的地方：

- `Unassigned`——机器人没有网络。修法是 `duckctl wifi connect`，而且必须走 BLE，因为
  `net.connect` 被刻意拒绝在 WebRTC 上（“一台从未见过网络的机器人无法通过那个网络被配置”）。
- `Unsaid`——一个来自 `btd` 广播地址之前的 release。fallback 照样回答；更新会让它变快。

它的第三个调用者不是上面两个：`install-dev.md` 开头就要“板子的 **IP 地址**”，还注明这个
镜像上的 mDNS 不可靠，却不提供获取它的任何办法。

### 2.2 `duckctl open`

解析，然后在浏览器打开 `http://<address>:8080/`。`--print` 改为打印 URL，供没有浏览器或脚本
使用；`--port` 用于以非默认 `--web-port` 启动的机器人。

做成一条命令而不是一段有文档的 shell 替换，理由只有一个：**端口默认值应当只存在于一个
人们永远不必去读的地方。** `open "http://$(duckctl ip):8080"` 能用，但它正是那种有人写一次、
然后永远查下去的行。

### 2.3 不是这些

- **`duckctl url`。** 那就是 `open --print`。第三条命令，其全部内容只是一个端口号。
- **`scan` 上的一个 URL 列。** `scan` 也列出耳机，而机器人行已经带着地址。列表下面一条
  指向 `open` 的说明就够了。
- **任何必须连接的东西。** 两条命令都是带 fallback 的广播读取。这里若有一条*要求* bond 的
  命令，会是另一种命令，而且它该归 `wifi` 和 `update`，而不是归“找机器人”。

### 2.4 这条循环闭合了什么，以及那一个后续

BLE 配置好网络，然后把它的 URL 交给你。两种传输不再是备选，而成为一个序列——值得点明，
因为 `route.rs` 刻意在 WebRTC 上拒绝 `net.connect`，而这正是那次拒绝的另一半。

后续，放在它自己独立的改动里而非这四项：`dev-push.sh` 的 `resolve_board` 变成
`client --name "$1" ip`，删掉内嵌的 Python 和 wrong-PIN 分支。独立是因为它触及推送路径，
也因为它应当在 `ip` 被人手工用过几次之后再落地。

`duckctl` 是手机 app 的临时替代，所以这保持在两条命令、不加新机制。耐用的两半是比它活得
更久的那两半：`btd` 广播地址，以及 `mediad` 在一个已知端口上提供服务。app 将原生地做同样
两步。

## 3. 这个工具以它即将不再是的那个传输层命名

**已决定并落地**——`duck-btctl` 是 `duckctl`，在它自己的 crate 里。本节其余部分是推理，
保留是因为各替代方案正是值得反复重读的部分。

`open` 在一个 http URL 上启动浏览器，而做它的那个工具名字里却写着 `bt`。值得深究，因为
结果它指向的东西比一条命令更大。

**`open` 本身没有放错地方。** 它的实质*就是*蓝牙：它扫描一个广播来得知机器人在哪里，
末尾的 `xdg-open` 只有一行。`duckctl open` 读作“用无线电找到机器人，然后给我看它的控制台”，
这正是它所做的——就像 `wifi connect` 是一条机制完全走 BLE 的 wifi 命令一样。

**这个名字仍是错的，原因随 `mediad` 而非随 `open` 而来。** 这个机器人即将有第二个传输层，
而两者按设计触及*不同*的方法集：`robot.move` 在 BLE 上被拒绝、在 WebRTC 上允许；`net.connect`
则相反。所以一个人两者都需要，而他们真正想要的不是一个二进制的选择——而是一个知道哪种
传输能服务一次调用、并在两者都不能时明说的工具：

> `wifi connect` 仅蓝牙可用，而这台机器人没有在广播。

那个工具不能叫 `btctl`。而一个叫 `btctl` 的工具，会在蓝牙刚刚不再是唯一途径的那个时刻，
悄悄教每个人相信蓝牙才是触达机器人的方式。

### 3.1 这是一次迁移，不是一次改名，而且它修掉了两个既有瑕疵

一个传输无关的客户端不能继续待在 `btd/examples/duck-btctl.rs`。它需要 `btleplug` *和*一个
WebSocket 客户端，而 `btd` 是 BLE 守护进程——它的一个 example 对其中一半来说是错误的家。
所以诚实的样子是它自己的 workspace 成员，而两件今天别扭的事在这途中不再别扭：

- **安装命令。** `cargo install --path btd --example duck-btctl` 别扭到 `dev-push.sh` 为从没
  跑过它的 clone 带了一个 fallback——它转而 shell 出
  `cargo run -q -p btd --example duck-btctl`。`cargo install --path duckctl` 不需要 fallback。
- **那个其实是产品的 example。** 它是 example 的原因，是为了让 `btleplug` 不上机器人，因为
  example 的 dev-dependency 从不进入已发布 artifact。它自己的 crate 免费保持这一点——通过
  不作为任何守护进程的依赖——同样的保证，只是直接声明，而非作为文件位置的一个副作用。

### 3.2 `duckctl`

它和 `robotctl` 的配对方式正是两者的实际用法：`robotctl` 在机器人上，`duckctl` 对着它。
它保留了仓库已经以之命名的 `duck-` 家族，而且短到无需别名就能输入。

`duck` 单独更好输入，但已被占用：Cyberduck 发布了一个同名 CLI，在 Mac 上很常见。
`microduck` 是仓库名，对一个每小时要跑二十次的命令来说太长。

### 3.3 什么没有被改写

约二十个文件里的 196 处引用，大多在散文里。**有日期的记录保留旧名。** `update-over-ble.md`
和 `install-path-gap.md` 描述的是一个时刻——一次更新会话、四个安装路径 bug 以及堵上它们的
东西——而把工具名改写进一段发生在该工具拥有它之前的事的记述，会让记录略微失真。它们的
*链接*被重指，好让它们仍能解析；它们的散文则不改。

`roadmap.md` 在同一目录，是例外，因为它不是对一个时刻的记录：它描述的是仓库*现在*的样子，
`roadmap.md` 在同一目录，是例外，因为它不是对一个时刻的记录：它描述的是仓库*现在*的样子，下到逐 crate 的布局表。一张指名不存在目录的布局表就是单纯地错。

**没有兼容 shim，没有别名。** 一个用户、一台机器人：一个仍能用的 `duck-btctl` 是第二个要同步的名字，也是让旧名在某人 shell 历史里再活一年的理由。

## 4. 页面变成控制台

**已落地**——`mediad/webclient/index.html`，仍是单文件，仍无构建步骤。

被允许的子集很大，而其中几乎没有什么是能从页面触达的。围绕一个人来此要做的事重新组织：

| | |
|---|---|
| **头部** | 机器人名、release、API 版本——来自 `hello` 和 `system.info`，通道打开时自动发送，而非点击 |
| **视频** | 外加来自 `getStats()` 的链路质量：码率、fps、丢包、RTT。今天，一条退化的流就是一张看起来更糟的画，和一段什么都不说的日志 |
| **驾驶** | 按键和一个屏上摇杆 → 以固定速率 `robot.move`；在视频上拖拽 → `robot.look` |
| **姿态** | `robot.enable`、`init`、`relax`、`stop`、`shutdown`——最后两个要确认 |
| **do / sound** | 作为菜单的 `Do` 和 `Sound` 枚举 |
| **遥测** | 以 2 Hz 的 `robot.subscribe` 进入一个实时面板：mode、health |
| **控制台** | 原始 JSON 框、日志、以及两个拒绝按钮——折叠着，因为它们证明的是路由表，而非驱动机器人 |

对它有三条约束：

- **停止按钮绝不能读成急停。** `route.rs` 允许 `robot.stop`，理由是这条通道可靠，且 deadman
  在 intent 停止到达时本来就会停下机器人，然后它白纸黑字说 UI 不该暗示它是物理急停。
  一个标签，而不是一个大红圈。
- **版本差异是横幅，不是锁死的门。** `hello` 报告偏差时它这么说，页面继续工作——与
  `duck-btctl` 在 #102 里定下的规则相同。
- **仍是单文件，仍无构建步骤。** 这条约束正是这个客户端根本能运行、并能存活的原因。如果
  它超出一个文件，就变成三个——`index.html`、`app.js`、`app.css`，三个 `include_str!`，仍无
  构建步骤，仍无 npm。

从页面驾驶，也是对 `remote-webrtc.md` 所下的两个声明、却没人演练过的第一次真实测试：
会话掉落时 deadman 会停下机器人（§6），以及 `control` 上的排序足以让 `intents.rs` 保持诚实
（仍是 §6）。两者都容易相信、错起来却很昂贵。

## 5. 机器人在会话开始前就自报名字

**已落地**——`mediad/src/producer.rs`。

`webrtcsink` 接受一个 `meta` 结构，信令服务器把它交给 `list` 里的每个 peer——页面已经在
记录它，而它是空的。从 `configd` 填充它：name、serial、release、`API_VERSION`。

很小，却回本三次：页面能在开始会话前叫出机器人名字，一个找到两个 producer 的客户端能
说出谁是谁，而 §7 的 rendezvous 服务恰好需要这个字段来路由。这里是成本最低的一项。

## 6. 它打开的是什么，又不是什么

一个面向服务端程序的表面。控制台的 `axum` 服务器让页面旁边的一个 WebSocket 看起来像又一条
路由，但驱动鸭子的程序按定义在局域网之外，而且它已经有传输层了：rendezvous 控制通道
（[`remote-access-design.md`](remote-access-design.md) §3.8）。这个监听器只为局域网内的一张
静止画面提供 `/frame`，对程序而言别无其它。

## 7. 顺序，以及还剩什么

四项改动，各自独立、分别落地，按此顺序：

1. **提供页面，在提供时把信令 URL 填进去。** 删掉了 python 指令和警告块。小，而且其上
   一切都更顺。API 版本以同样方式替换，供 §4 的横幅用——页面里的字面量会是 `API_VERSION`
   的第二份副本，在被 bump 的那天错，而且错在报告一致的方向上。
2. **Producer `meta`。** 更小，且独立。
3. **`duckctl` 获得 `ip` 和 `open`。** 仅客户端，不碰任何守护进程。
4. **控制台。** 大的一项，最后做，做在一个本已可达的页面上。

**没做、且刻意独立：** `dev-push.sh` 的 `resolve_board` 仍用 `duckctl wifi status` 和六行内嵌
Python 手写这个（§2.4）。它变成 `duckctl ip`，从而删掉 Python 和 wrong-PIN 分支——独立是因为
它触及推送路径，也因为它应当在 `ip` 被人手工用过几次之后落地。

## 8. 不做的事

- **给控制台加一道门。** `remote-webrtc.md` 的 §4 拥有那个决定，这里没有任何东西改变它的
  条款。一个关掉页面的 `--no-web` 标志，对那一节标记的家用情形值得拥有——一个标志，不是
  一个机制。
- **JS 框架、bundler 或 `gstwebrtc-api`。** 页面手工说协议，因为一个需要 npm 的客户端是一个
  没人会跑的客户端。到四倍大小依然成立。
- **通过 TLS 提供。** §1.3 说了何时，以及为何不是现在。
- **教广播一个端口。** 它携带的是四个字节的 IPv4；一台跑在非默认 `--web-port` 上的机器人，
  是 `duckctl open` 上的一个 `--port`，而非线格式的改动。
