# 手机 App —— 它由什么构建

状态：已建 · 日期：2026-09-17 · 负责人：pierre

主人的 App：让机器人站起来、把它放到 wifi 网络上、更新它、登录它、驾驶它、看它是否安好、请它做它知道的事。它用什么写的、它从我们已经为另一台机器人发布的 App 借了什么，以及机器人还欠它什么。

它住在 **[`pollen-robotics/microduck-app`](https://github.com/pollen-robotics/microduck-app)**，那里是代码和运营那一半——构建它、签名它、弄到手机上——的地方。这一页是推理：为什么它长成这样，以及哪些决定花代价。

[`app-path-design.md`](app-path-design.md) 的伴侣，它拥有机器人侧——GATT 面、路由表、通道、配对、身份，以及关于它们的每个开放问题。两处相接的地方，那一页是主人、这一页指向它。[`remote-webrtc.md`](remote-webrtc.md) 拥有另一条传输，§1.2 是两者之间的线。

## 1. API 是规范；App 是客户端

`btd/src/route.rs` 决定一部手机可以要什么，而 [`duckctl.md`](../robot/duckctl.md) 是 App 拥有的最接近功能规范的东西——它里的每条命令都是 App 能做的一个调用，走同一条无线电、带同样的应答。

| 屏幕 | 调用 |
|---|---|
| 选机器人 | 广播——名字和 IPv4——然后 `hello` 和 `system.authenticate` |
| 机器人 | `system.info`、`robot.health`、`system.services`、`system.setName`、`system.reboot`、`robot.init`、`robot.enable`、`robot.rebootMotors` |
| 驾驶 | WebRTC：视频、`robot.move`、`robot.subscribe` |
| 动作 | `robot.skills`、`robot.do`、`robot.policies`、`robot.loadPolicy`、`policy.check`、`policy.search`、`policy.fetch`、`policy.install` |
| wifi | `net.status`、`net.scan`、`net.connect`、`net.forget` |
| 更新 | `update.check`、`update.apply`、`update.subscribe`、`update.status`、`update.listInstalled`、`update.log`、`update.rollback`、`update.select` |
| 日志 | `system.logs` |
| 账户 | `account.login`、`account.status`、`account.logout` |

任何它最终需要、却未被路由的东西，是对 `route.rs` 的一行改动，以及一个关于它是否属于无线电的决定——那是 §3.1 存在要给我们的性质。App 现在已测试那个性质五次：`update.rollback` 和 `update.select`，然后 `robot.init`，然后 `robot.enable`，然后 `robot.rebootMotors`，每一个被打开都因为用 App 发现那个拒绝花了拒绝自己的推理没算到的代价。

### 1.1 它是机器人的界面，不是设置工具

被路由的子集曾是 wifi、更新、健康和一个名字。它现在是人对鸭子做的大部分事，而 `route.rs` 每一臂上的论证押韵：**十米无线电范围意味着无论谁点它都在看着机器人，且配对经过 PIN 检查**——所以 BLE 是最能回答*谁在看*的传输，那是那个文件里大多数拒绝所开启的东西。

这就是为什么下面的机器不是过度工程。一个设置工具能用一个调用和一个转圈蒙混过关；一个界面不能。

留在无线电之外的东西：连续意图和任何推流（`robot.move`、`robot.subscribe`、`tof.stream`、`pad.input`）、配对 PIN、`update.pin` 和 `update.resetToGolden`，以及那个唯一结果是地板的调用——`robot.relax`。第一组属于另一条传输；其余属于机器人上一个终端前的人。

`robot.rebootMotors` 曾在最后一组、现在不在了，这一对值得理清：松软一台正撑着自己的机器人*产生*跌倒，而重启一个锁存了过载的舵机恢复一台早些时候就停止撑自己的机器人——而在它被路由之前，App 能在 `robot.health` 上点名跳闸的关节、却只能提供 ssh。`route.rs` 里那一臂带着推理。

### 1.2 两条传输，它们不是对手

除 `drive` 外上面一切都走 BLE。**BLE 是 App 的通道，因为机器人侧那一页 §2.2 存在的原因**：无需网络就工作的设置。一块板子到达一个新地方，它认识的 wifi 不在，网络上没有任何东西能到达它——一个需要 LAN 才能改设置的 App，修不了那个让机器人离开 LAN 的设置。

`drive` 按定义需要网络，并从 `net.status` **经无线电**拿到要用的地址。那是两者作为一个东西而非两个工作：总工作的传输告诉你如何到达快的那个。机器人自己的控制台也不是竞争者——它需要地址，那意味着它需要网络，那意味着它需要 App 存在的目的。

## 2. `reachy_mini_mobile_app` 是参考，不是基座

Pollen 为 Reachy Mini 发布一个 Tauri 2 App——React 19、MUI、`tauri-plugin-blec`、TestFlight 和 Play Internal。它经 BLE provision 一台机器人、然后经 LAN 和 Hugging Face 做其他一切。

它的 BLE 层说一种不同方言——四个特征、命令作为字符串、应答按子串解析（`ERROR:`、`OK:`，以及 `ECHO:` 表示「你固件太旧不认识这条命令」），它自己的源码称之为一次性测试面。而它的蓝牙存在是为了跑**一次**，§4 是我们不能继承的原因。第二个决定这个 App 的形状，而不仅是它的传输。

值得拿的是管道，那里是昂贵知识所在：

| 作为代码拿 | 作为规则拿 | 留下 |
|---|---|---|
| `tauri-plugin-blec` 接线——但**不是**他们 vendor 的 `btleplug` 补丁、也不是他们的 npm 绑定。那个补丁存在的 CoreBluetooth 连接崩溃（deviceplug/btleplug#397）在 `btleplug` 0.13 上游修好，`blec` 0.14 建在它之上；他们的 0.8 早于它。而他们维护的 crate-to-npm 锁步，从不到达一个由 Rust 驱动的客户端，因为 webview 不调 BLE | 不过滤地扫描并甄别你自己的候选——他们的扫描核心和 §3.3 各自到达这里，那是它真实的证据 | TanStack Query：它在 HTTP 上缓存服务器状态，而这个 App 没有 |
| Android BLE 运行时权限处理，那是用 `blec` 而非裸 `btleplug` 的原因 | 轮询候选而非睡一觉后取一次快照（§3.4） | 设置向导状态机——§4 |
| 边到边、`viewport-fit=cover`、安全区插图、竖屏锁 | 每个错误带它恢复到哪一步，所以「再试」不重启流程 | 字符串匹配的错误分类：`configd` 以类型返回 `BadKey` 和 `NotFound`，缺失的方法自称 `METHOD_NOT_FOUND` |
| 他们的 App Store 合规和审核笔记，写一次、花一次拒绝学到 | App 后台时 BLE 掉线是预期、不是故障：iOS 会拆 GATT 链路 | |
| `x25519-hkdf-sha256-aesgcm` 密封密码方案，如果机器人页 §8.1 落在密封而非链路层——线格式在他们侧有文档、且有可用来测实现的客户端 | 一次失败连接可能看起来像成功、然后挂在订阅；断开重连强制一次新发现 | |

## 3. 协议住在 Rust 里

`tauri-plugin-blec` 同时暴露 Rust 处理器和 JS 处理器，且是*同一个*处理器——从任一侧打开的链路都能从两侧驱动。所以 App 依赖 `duck-ipc-proto` 拿线类型、依赖 `duck-ble` 拿分块和 GATT UUID，从 Rust 驱动无线电，并把有类型的命令交给 webview。React 从不解析机器人应答；它调用返回 `NetStatus` 的东西。

这是要紧的重用，也是 Reachy Mini 不可能有的：**App 不能漂离守护进程。** 一个协议改动像失败 `btd` 的路由表一样失败 App 的构建——这在愤怒中发生了两次，两次都抓住一个否则 App 会在坏时刻从机器人那里学到的字段。

这也是 Tauri 对替代方案的论证，而非通常那个。每个跨平台工具包给你一份代码库；只有这个让客户端说服务器自己的类型。

**`duck-ble` 因为这个 App 存在。** `gatt`、`framing` 和 `adv` 曾是 `btd` 的，每个都在它住的地方被标为线契约——`adv` 直说一个在客户端单独写的解码器只会与自己一致，这个 App 在 crate 存在前手工卷了一个证明了它。抽出它们停住了一个手机二进制为某个模块的份背 `clap` 和 `tracing-subscriber`，也停住了 `duckctl` 为三个平台无关文件编译一个 Linux 守护进程——在 Linux 上，还有 `bluer` 和一个 vendor 的 libdbus。

### 3.1 媒体在哪，以及为什么那不是这个里的洞

协议不在 Rust 里的唯一地方是 WebRTC 数据通道，且只一半。对等连接和 `<video>` 本质上是 webview 的；没有 Rust 等价物能把帧弄到手机屏幕上。但数据通道携带*同样*的 JSON-RPC，所以在 TypeScript 里手写那些信封会重新引入这一节安排要防止的漂移。

所以 webview 搬字节、Rust 决定它们是什么：每一行由 `proto::Request` 从一个 `proto::Call` 构建，而 App 的信令模块完全不包含方法名。`.ts` 文件里的一个 `{vx, vy, vyaw}` 对象字面量会继续编译、并开始错误转向。

### 3.2 那具体删掉了什么

Reachy Mini 的传输写一条命令、同步读响应特征，然后——如果应答是 `OK: working` ack——等一条带真实负载的通知。一个快应答可能*早于*那次读到达，那让负载孤儿在积压里、留给下条命令的等待消费：这就是一次 wifi 扫描在手握上一条命令的密钥交换对象时返回空的原因。修法是每条命令顶部的一次过期积压清除。

这些在这里都不可达。JSON-RPC id 按构造配应答到请求、一个特征意味着没有写-到-通知关联可猜，且机器人页 §3.2 已让机器人丢弃一个属于它主人的会话。值得写下、好让没人好心地把绕行连同传输一起移植。

## 4. 蓝牙是永久通道，不是设置步骤

一个结构差异，且它决定 App 的形状。

Reachy Mini 的 BLE 代码跑**一次**——一个带终态、之后 LAN 接管、蓝牙永不使用的向导。鸭子的 BLE 是机器人界面住的地方，只要机器人存在。

所以这不是一个焊上设置页签的向导。App 有一个会话层，它不说就重连、重新认证，因为 §3.2 让 `btd` 在中心离开时丢弃会话、一个重连的手机以未认证开始。每个屏幕容忍它下面的链路掉线并回来——包括更新期间，那里 `btd` 在应答发出五秒后重启（[`restart-order.md`](restart-order.md) §1），以及用户跑去浏览器批准一个设备码时，这就是 `account.login` 以码而非 token 应答的原因。

机器人半路迎接那层：`updaterd` 每组件保留最新进度并重放给新订阅者，`update.status` 在更新期间从缓存快照应答。所以一部更新中途重连的手机会重新认证、重新订阅、并被告知走到哪了。

**那层是 App 真正的核心，且它结果可测。** 机器人页 §8.2 说值得测的场景在板外不可测——对房间里三台机器人真、对一个掉线的链路不真。`tauri-plugin-blec` 随附一个进程内 mock、按需掉线和挂起操作，所以重连、重新认证和重新订阅是普通测试。它们抓了三个真缺陷：打开链路的调用上订阅发了两次、一个因发现缓存清空找不到自己机器人的重连、以及一个从没 up 过的链路的 `Down` 事件。

## 5. 它自己的仓库

守护进程 workspace 共版本，因为里面一切随一个工件发布。App 以不同节奏发到应用商店、不属于那条版本行，所以它有自己的一条。

`microduck` 是公开的，所以 `duck-ipc-proto` 和 `duck-ble` 是普通 git 依赖、什么都不需要凭据。依赖刻意跟踪 `main` 而非钉住的修订版：一个弄坏 App 构建的协议改动是这个安排存在要给的信号。

## 6. 版本下限，与守护进程规则相反

**App 在握手时拒绝一个低于 `API_VERSION` 31——机器人 0.14——的机器人。**

这刻意不像守护进程遵循的规则。`app-path-design.md` §3 强调版本差异报告、从不拒绝，那对守护进程对：它是为一台没有网络的机器人存在的传输，那里 `net.connect` 是走出漂移的路。

App 做了不同交易，交易买来的是每个屏幕。一个下限、查一次，意味着一个屏幕能把一个字段当存在、把一个方法当已路由、把一个应答当守护进程定义的形状——而不是每个都带自己对一台更旧机器人可能发了什么的猜测。在握手时发现，也胜过四个屏幕后从一个不存在的方法发现。

**代价是真实的、且在拒绝自己的话里**：一台低于下限的机器人不能*从手机*更新，因为手机不跟它说话。`duckctl update apply` 走同一条无线电到达它，消息这么说。

一台比 App *新*的机器人被服务。协议只增字段，而一个拒绝它不认识的东西的客户端会需要与每台机器人同步更新。

## 7. 机器人还欠 App 什么

这些每个都由 [`app-path-design.md`](app-path-design.md) 拥有；列表的意义是它们都面向 App。

| | |
|---|---|
| **加密**——§5.5、§8.1 | 机器人到任何人手里前必须闭合的东西：一个工作是写 wifi 口令的 App，不能*发布*在一条明文携带它的链路上。它不阻塞构建——§8.1 的三个候选修法有两个不需要配对，所以 App 无论如何都对着开放链路写 |
| **`identify`**——§8.2 | 让*这台*机器人做点什么，好让三个名字的列表变成你手里的鸭子。解了三分之二：`robot.do` 和 `robot.sound` 都被路由——`duckctl quack` 是第二个——而 §8.2 那个「没有东西驱动扬声器」的说法过时了。剩下的：它必须在认证*之前*工作，因为当问题是把 PIN 对准对的机器人时，先要 PIN 是循环的。Reachy Mini 的 `PLAY_SOUND`——显式公开、无 PIN、从扫描列表播放——是要抄的形状 |
| **每机器人 PIN**——§5.3、§8.2 | 没有东西生成、打印或记录它，且它不能从身份派生、因为身份被广播。等硬件 |
| **配对撤销**——§5.6 | 「忘掉这部手机」是设置 App 的基本项、没有 API |
| **工厂重置**——§8.2 | 没有东西清 `configd` 的配置，所以一个 provision 的名字和一次用户改名无法区分 |
| **手机连接时重连的手柄**——[`pad-minimal-pairing.md`](../project/pad-minimal-pairing.md) 故障 3 | 当 `btd` 持有一条外设链路时，控制器不会以中心发起，所以会话期间打开的一只已配对手柄就那样坐着。无守护进程修法：明显的是那个失败的调用。App 能应请求让出它的链路二十秒；在那之前答案是先开手柄 |

靠用 App 而定，并因为每个都是拒绝自己的推理在与它拒绝的东西接触后没挺住的拒绝而命名：

| | |
|---|---|
| **让机器人站起来**——#301、#303 | `robot.init` 被拒因为它「要做事的人看着机器人而非屏幕」，那是 `route.rs` *为*路由 `robot.do` 和 `policy.install` 做的论证。`robot.enable` 作为遥操作被拒，而它不是——一次请求、不是每秒五十次。没有两者，App 能展示机器人关于自己的一切却不让它动，出去的路是去找手柄 |
| **一条通知携带 512 字节**——§3.6、#292 | 这个 App 发现、用 `duckctl` 复现：`btd` 把应答定为 `mtu - 3`，对着 CoreBluetooth 的 517 MTU 比一个特征值可容纳的多两字节。中心保留前 512、静默丢剩下的，所以 `{"security":…}` 到达时是 `{"serity":…}`——或当丢的对是换行时，是一个从不应答的调用 |
| **三台里哪台是我的**——§8.2 | 名字来自 SoC 序列号、广播带 IPv4，所以第一屏不连任何东西就列名字和地址。App 以序列号为键、把地址当缓存，那正是 §8.2 的规则逐字：一个被另一块板子复用的记住的地址按名字拒绝、而非静默采用 |

## 8. 开放

- **PIN 屏幕。** 出厂 PIN 是 `000000`、在这个仓库公开，所以今天的 PIN 步骤要一个什么都不保护的秘密、并在摩擦最贵的那个流程里加一屏。App 静默发它。当有一个打印的每机器人 PIN 可输时屏幕出现，那也正是「PIN 错、剩两次尝试」会住的地方。
- **手柄，从手机。** `pad.pair`、`pad.forget`、`pad.bind` 和技能表编辑被路由却未触达。`route.rs` 说 BLE 是 `pad.bind` 存在的原因——抱着机器人的人抱着手柄——而上文故障 3 是从手机配对比路由暗示的更难的原因。
- **一个 App 是否最终服务两台机器人。** 现在不——它意味着发布代码库里的第二种方言，而流程只共享一个传输。如果它成为目标，前提是*协议*收敛、而非 UI。
- **UI 套件。** 没有：App 约三百行 CSS。MUI 是明显候选、未被采用，迄今没有任何东西想要它。如果某个屏幕需要样式表给不了的组件，值得看一眼，不值得第二眼。
