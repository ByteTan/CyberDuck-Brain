## 我们在哪

| | |
|---|---|

| `duck-control/` | 机器人模型 · 总线 · IMU · `RobotIo` · 观测 · ONNX 策略 · 安全。一个库：无 tokio、无套接字、无 systemd |
| `duck-ipc-proto/` | 每个 `*.` 命名空间的线契约，在 API v14——只有 serde/serde_json/semver，所以恢复路径上没有任何东西链接引擎的树 |
| `robotd/` | 一个 50 Hz 循环，通过安全层驱动走/站/滚、意图、来自截止期遵守和策略状态的健康。自 M3 起：运动学、接触里程计、注视 IK、声音、ToF 特雷门琴和合唱，都挂在同一个节拍上（[`robotd-design.md`](../design/robotd-design.md) §4.4–4.5） |

| `configd/` | NetworkManager 之上的 wifi、机器人名字和由 SoC 序列号派生的身份、配对 PIN、重启、unit 报告。`--fake-net` 在板外服务整个面 |
| `btd/` | BLE 传输适配器——帧、被路由的子集、BlueZ 后端、配对代理。在硬件上工作，默认未加密——[`app-path-design.md`](../design/app-path-design.md) §5.5 |
| `duckctl/` | 从笔记本电脑访问机器人。今天走 BLE；以机器人而非无线电命名 |
| `mediad/` | 摄像头、麦克风、编码和 WebRTC 网关，加上它服务的控制台。**从一块 Radxa Zero 3W 推流到局域网浏览器**、经 `mpph264enc` 的硬件 H.264、旁边带 `control` 数据通道 |
| `tof/` | `tofd`：头部的 8×8 ToF 矩阵在自己的套接字上、15 Hz。一块没装传感器的板子照样跑它并说明 |
| `xtask/` | 打包 · 签名 · 晋升——字节一致的晋升已验证 |
| `.github/` | ci · release · promote · dev——四个都真跑；自 `0.2.0` 起的每个发布都经它们到达一块板子 |
| bootstrap | `updaterd install` + `scripts/install.sh`——机器人通过**普通引擎**装它的第一个发布，所以没有 bootstrap 专属代码路径可漂移 |
| recovery | `robot-boot-check.timer` + `robot-rescue` + `golden` 符号链接随附并启用。**从未在板上演练过**（[`boot-recovery-net.md`](../design/boot-recovery-net.md)） |

| missing | App、SDK、策略通道、自主大脑，以及从局域网之外访问机器人 |

## 第一份路线图达到了目标

M1 到 M4 是一条序列、一个目的地：一台会走路、能无线自我更新、且这样做时不会被变砖的机器人。那个到了。自 `0.2.0` 起的每个发布都经 M1 和 M2 建的机器到达一块板子，而 `0.9.x` 是一只会走、会滚、会看、会说、会唱的鸭子。

接下来的不是那条队列的延续。剩下的工作是独立轨道、风险不同、彼此之间没有顺序，所以**下面的数字是标识符，不是序列**——[工作顺序](#工作顺序) 是它自己的一节。

**创始论断对了一半。** *难的是产品化而不是能力*正确地判了难度：更新路径、健康门控、恢复网和 BLE 面都建起来了、都站得住。它判错了体量。自 `0.5` 以来几乎所有东西都是能力——运动学、里程计、ToF、注视、声音、合唱、摄像头——而其中最大的一块，自主大脑，仍未移植。

## 里程碑

每个都有一个说「完成」的测试，因为没有测试的里程碑会漂移。

### M1 —— 闭环 · **完成**

更新器有了真实的东西来门控，团队有了一个共享 crate 边界：一个状态是原子量而非互斥锁的 `robotd` 骨架（一个循环被卡死的机器人必须仍能应答*我不健康*）、`duck-ipc-proto` 被抽出、这样恢复路径上没有任何东西链接引擎的 http/tar/crypto 树、一个作为真实套接字探测的健康门控、`robotd` 套接字的单一真相来源、每个守护进程在**任何东西可能失败之前**以 `warn` 记录的一行身份，以及经普通引擎的首次安装 bootstrap。

**完成：** `robotd/tests/updater_gate.rs` 走真实套接字对真实 `robotd` 进程门控一次更新并提交；`robotd --unhealthy` 回退 `current` 后面的内容。

### M2 —— 开发通道 · **完成**

`sudo robotctl update apply daemon --ref my-branch` 安装一个分支构建，`scripts/dev-push.sh` 通过 ssh 安装一个笔记本构建、完全不跑 CI。两个性质让它在每次推送上都安全，且都在工作流之外强制执行：开发构建**不能成为 `latest`**（版本是 semver 预发布、`version_under` 拒绝把一个 dev 标签读成发布版本），且它**不能装在客户机器人上**（那里 `allow_dev_keys` 为假，而一个受信任密钥只有文件名以 `.dev.pub` 结尾才算开发密钥）。

**完成：** 针对真实仓库验证——`dev.yml` 发布、`--ref main` 通过网络安装、一个客户机器人配置拒绝同一个构建。

**它留下的一件事，现已决定：** 一个私有仓库的发布资产要用 token 才能到达、而客户机器人没有，所以这个仓库私有期间，野外的机器人什么都下载不了。**决定是发布它**，那解决了它且不改任何代码——引擎用的 API 路径对公开仓库也有效（[`updater-design.md`](../design/updater-design.md) §6.1）。

### M3 —— 真正的 `robotd` · **完成**，两片

`robotd` **替换**了 `microduck_runtime`，办法是把它的控制核心抽进 `duck-control` 而不是重新实现，所以奇偶性作为抽取的后果到来，而不是一场对移动靶的赛跑。Slice 1 是一个真正的 50 Hz Dynamixel 循环保持它的姿态——这让 `robot.health` 意味着*循环在满足它的截止期*。Slice 2 是一个 61-D 观测构建器、主加站立策略、意图面，以及一个走它的游戏手柄客户端。

**安全权威在这里落地而不是 M6**，握着总线上唯一的写句柄，所以没有策略、没有客户端*能*绕过它命令电机：关节钳制、跌倒 → 松软，以及意图 deadman。

**硬件先行、仿真在后**——而且板子产生了测试造不出的那一个 bug：`ort` 在低于其下限的运行时上*恐慌*而不是报错，杀掉了控制线程、让健康怪错了东西。

**完成：** 三个都在一块 Radxa Zero 3W 上。它经意图 API 驱动走路；用 `robotctl` 应用的一次更新干净地重启它、门控通过；一个起来就不健康的发布自己回退。

### M4 —— 硬件 bring-up · **收尾中**

一个测量里程碑、不是功能里程碑：它存在是为了把猜测变成真实 Radxa 上的数字。几乎全部作为发布的副产品被回答了——循环在非 RT 内核上保持 50.0 Hz（15022 个节拍里 `missed=3`）、总线和 `imu_to_dxl` 板在 `/dev/ttyS2` 上应答、每个区域都有一个真实温度读数、`on_apply` 里的 `systemctl restart` 对真实 systemd 有效、门控真实地提交和回退。

**日志保留问题靠决定而不是测量解决。** `/var/log` 在这个镜像上是一个 zram 设备，所以 `Storage=persistent` 给 journald 一个本身就在内存里的目录：它挺过干净 `reboot`、断电时丢掉最近的日志。那是刻意的安排——持久记录是 `/var/lib` 下的更新历史、每条 `fsync`（[`deploy/README.md`](../../deploy/README.md)）。所以原来「日志挺过断电」的标准退休了：它要的是这个项目决定不要的一个性质。

**完成当：** 它在硬件上走路、经 `robotctl` 应用的一次更新干净重启 `robotd` 且门控通过、且重启后 `journalctl --list-boots` 报告上一次启动。前两个已做；最后一个是板上一条命令、是唯一悬而未决的。

**两个数字刻意留作不测**，因为没有东西等它们：eMMC 写时序和负载下的电池。它们属于 M7，那是关于知道一块板子在做什么的里程碑。

### M5 —— `mediad`、WebRTC、SDK · **进行中**

**落地了，在硬件上。** `mediad` 随发布发布、作为自己的 unit 运行。摄像头经 VPU 到达局域网浏览器——`mpph264enc` → `webrtcsink`、约束 baseline——带一条携带每个其他传输都说的同一套 JSON-RPC 的 `control` 数据通道，控制台由机器人自己服务，所以有一个 URL、无需安装（[`remote-webrtc.md`](../design/remote-webrtc.md) §0、[`webrtc-console.md`](../design/webrtc-console.md)）。两个 GStreamer 插件必须从源码构建才能到那里（[`media-bringup.md`](media-bringup.md)），此后摄像头经 `rkaiq` 得到了 3A。

**三件事让它开着。**

**局域网之外。** 同样的设计、前面加一个 rendezvous 服务和 TURN（§7），刻意第二个建。[`remote-access-design.md`](../design/remote-access-design.md) 现在拥有它：一个经 OAuth 设备流到达的 Hugging Face 账户，以及从 mini 机队已在用的 rendezvous Space 到机器人上已有信令服务器的一座桥。

**账户**建好了、是前半——`robotctl account login` 打印一个码，某人在 hf.co/oauth/device 批准它，机器人持有一个自己续期的凭据；同样的三个调用在 BLE 上有效，那是没 wifi 的机器人仅有的传输，也在数据通道上有效。还没有任何东西消费那个凭据：**桥**是下一步，而那里 rendezvous Space 的协议原来是 HTTP 而不是局域网客户端说的 WebSocket。

鸭子带着它发布前要修一件事：token 携带 Hugging Face 授予的每个 scope，因为第一方设备码客户端不取 `scope` 参数。把它缩到 `openid profile read-repos` 是组织里的一个公开 OAuth App 和一个常量。

**SDK，以及一个小 Python 客户端。** 传输问题已答：控制走 rendezvous 控制通道（[`remote-access-design.md`](../design/remote-access-design.md) §3.8），那是 HTTP 上的 JSON-RPC、无 WebRTC、从数据中心到达鸭子。视频是 WebRTC 之上的可选附加，`media.stream` 是后备。`spaces/shared/` 已经有三块——`rendezvous.py` 找鸭子、`wire.py` 带调用、`control.py` 配应答——所以 SDK 是那些、打包，Spaces 导入它而不是保留自己的副本。

**隐私，现在它是两项而非一项。** *同意*——流开始前逐会话的明确批准——是一个 `mediad` 会话层改动、不阻塞于任何东西。*可见指示器*需要一个软件控制的 LED，这个硬件上不存在（[`remote-webrtc.md`](../design/remote-webrtc.md) §11）；它是硬件问题、该问硬件，而不是停在软件里程碑上。`architecture.md` §7 说得对：两者现在都便宜、以后都贵，所以同意不该等 LED。

**完成当：** 遥存在局域网外可用，且一个服务器端脚本能在几十行里取一帧、发一个意图。

### M6 —— 发布就绪

陌生人需要什么。预售开着，所以这按**前置时间**排而不是按难度——代码最少的项前置最长。

- **配对 PIN。** BLE 配对安全靠一个每机器人的 PIN；出厂默认是 `000000`、且在这个仓库里公开，所以开箱时配对只证明物理在场、别的没有。得有东西生成一个、打印它、记录打印了什么——一个工厂流程、不是补丁。它不能来自身份，身份是发布在广播里的。
- **标定**，provisioning 的另一半。身份不再等它：机器人从它自己的 SoC 序列号派生一个并自称 `duck-c51b`。
- **恢复网，在板上演练。** 它建好、发布了，却从没对过一个其守护进程起不来的发布跑过，而那才是唯一要紧的路径。这里最便宜的一项：一块板子、一个刻意坏掉的发布。
- **同意**，来自 M5。
- ~~**Manifest 过期报告**~~（§8.4.2），**完成**：`robotctl health` 说更新源上次何时应答、上次检查为什么失败，并在沉默一周后警告。
- **权限仲裁**，完成——包括 #52 暴露的边缘：`Call::is_mutating()` 没覆盖 `robot.enable`，所以那个让策略在一台走路的机器人上跑起来的调用被和 `hello` 分到一类。
- **App。** #107 设计它、什么都不建。阻塞是一部手机尖峰——scan、connect、`hello`、authenticate、`--require-pairing` 开启的 `system.info`，在真 iPhone 和真 Android 上——因为 §5.5 目前是一个关于笔记本上 CoreBluetooth 的事实。

有一项靠被决定而离开 M6：客户机器人从哪下载。决定是发布这个仓库，所以一台已发布的机器人无需 token、无需第二个主机就能到达它的发布。它留下的后续是预算而非阻塞——匿名 GitHub API 请求每小时每 IP 上限 60，一只鸭子离得远、一条 wifi 上一个房间二十只不是（§6.1）。

**完成当：** 一个非开发者从手机更新机器人，且一个刻意变砖的发布无需笔记本就能恢复。

### M7 —— 知道一块板子在做什么

一只在别人手里的鸭子会出故障，而今天对*哪个部分*的答案是一个开发者通过 ssh 读日志。这个还没有形状；它是一个开放调查，问题就是它拥有的东西。

**已存在的**比看起来多：`robotctl health` 报告总线、IMU、电池、每电机温度和 SoC；`robotctl monitor` 画出循环、手柄流、ToF 矩阵、3D 机器人和一行电源；`scripts/pad-stack-report.sh` 是把一个子系统整个故事收进人可粘贴的东西的先例；`board-test.sh` 跑 60 项检查，但在 CI 里仿真 aarch64 上、而非你面前的板上。

**缺失的，作为问题：**

- **一个支持包。** 一条命令，出故障后，产出一个可发送的文件。没有东西把健康、版本、日志、更新历史和 unit 状态收在一起。`robotctl update show` 是对一个子系统的形状——一份持久的每次运行记录、把那个时间窗的日志拼进来——且只覆盖更新。
- **一个非开发者能跑的硬件通过/失败。** 总线扫描和每舵机应答、IMU 理智、ToF 在场、摄像头在场、NPU 在场、麦克风和扬声器、负载下的电池。精神上更接近 `board-test.sh`、瞄准硬件而非发布。
- **历史，因为间歇故障在快照里不可见。** 总线读失败、错过的节拍、舵机温度峰值、欠压。日志按设计挺不过断电（M4），所以这里要紧的任何东西都需要更新历史的持久性而非日志的。
- **与 #52 的重叠。** IPC monitor 设计是这个同一问题的软件一半，而它的崩溃记录——最后事件刷进 `/var/lib` 下一个固定大小文件、在发布目录之外以挺过更新和回滚——正是硬件故障报告需要的那个持久性。两者该一起决定，而不是长出两个答案。

M4 的两个未测数字落在这里：eMMC 写时序和负载下的电池。

**完成当：** 一个非开发者能在故障后跑一条命令、产出点出故障部分或说硬件没事的东西。

### M8 —— 策略通道：来自 Hub 的策略

每个策略过去都随**守护进程工件**发布，所以一个新步态要一次守护进程发布，一个在笔记本上训练的策略 only经 CI 或整个守护进程侧载到达鸭子。这个里程碑的意义是：一个在 `microduck_rl`——那个私有的训练仓库——里训练的策略能被发布、安装、在它自己的版本行上试用，而且一个人能试一个他没训练过的、并回来。

**已设计**，在 [`policy-channel-design.md`](../design/policy-channel-design.md)，它拥有这一节过去留空的决定。简短版：一个槽位从三个来源之一填——official（`pollen-robotics/*`、重置目标）、community（任何其他 Hub 仓库、未签名、被报告但从不动自动应用）或 local（板上的路径）；`policy load` 写配置键、`policy reset` 删它，所以持久化和撤销是已存在的机制；官方策略集作为一个 `policies` 组件发布而非每槽位一个。

**引擎大部分已建：** `hf_hub` 源解析并校验、一个组件带自己的版本行、回滚、钉住、启动试运行和已知坏历史、`on_apply = reload` 存在、`xtask sign` 签任何工件目录。

**三片，各自单独有用：**

1. **本地循环、无网络。** `robot.loadPolicy` 加家姿势重载，以及 `robotctl policy list` / `load` / `reset`。端到端交付「不改 toml 就试一个策略」，不碰 Hub 和发布决定。`API_VERSION` 17 → 18。
2. **官方策略离开工件。** *完成。* `robotd` 读 `/opt/robot/policies/current`，`scripts/seed-policies.sh` 从 `pollen-robotics/microduck-policies` 下载钉住的策略集来填它——`setup-board.sh` 已为 ONNX Runtime 用的那个安排。`policies/` 和它的三个 `--include` 列表没了，而把 `[workspace.metadata.policies]` 升一级就是发布一个步态的全部。
3. **越过钉住版本。** *完成。* `updaterd` 上的 `policy.*`、`robot.reloadPolicies`，以及 `robotctl policy check` / `update`——一个重新训练的步态现在无需守护进程发布就到板子，那正是里程碑的全部意义。每个策略集记录它来自的仓库，所以没有东西配置它两次。
4. **社区库。** *完成。* `policy load <slot> <org/repo>` 从任何 Hub 仓库抓一个策略到 `/var/lib/robot/policies/<org>/<name>/<rev>/`，`origin` 对陌生人的报 `community`，`policy search` 列出外面的东西。迄今发布的仓库已经带一个含 `obs_len`、`action_len` 和 `model_api` 的 `manifest.json`，所以一个在这里跑不了的策略在下载前被拒——那也正是 `model_api` 停止「已设计未实现」的地方。

`reset` 在三个里都意味着「移除覆盖并重新解析」，所以 slice 1 对发布内副本送出一个正确的重置，而 slice 2 改它解析*到*什么、不碰命令。

**真正缺的**在两端、不在中间：

- **`robotd` 不能按需重载。** 机器存在——`robot.setMode` 已在家姿势重建每个 ONNX 会话——但没有每槽位触发器，且一次失败的加载必须保留运行中的控制器而非让机器人无步态。
- **没有东西发布一个包。** `xtask package --channel` 接近了；它把 `--version` 对 crate 版本检查，而策略集没有那个，且 HF 仓库布局不存在。
- **`model_api`** 两边都设计好、未实现。`robot.modelApi` 应答，没有东西查询它。
- **训练循环。** `microduck_rl` 导出 ONNX；没有东西把结果带到板子。Slice 1 是让「训练它、试它」成为一分钟而非一次 CI 运行的东西。

**完成当：** 一个在 `microduck_rl` 里训练的策略被发布到 Hub、装到一只鸭子上、试用、并用 `robotctl policy reset` 撤销——控制循环在整个过程中从不丢电机控制——且一个没训练它的人能从机器人找到它并试它。

### M9 —— 自主大脑

最大的未跟踪缺口：运行时的 `autonomous.rs` 在守护进程里哪都不存在、没有设计文档拥有它。[`ideas/autonomous_behavior.md`](../ideas/autonomous_behavior.md) 是暂存处——一个基于能量/心情模型的 16 状态机、新奇度网格探索、ToF 避障、惊吓、声音反应、玩球、一个打盹循环、抚摸。

它需要的每个输入现在都存在，有些它从没有过：环境声音事件、深度帧、分类的躯干帧障碍点、语音标签、按稳定 id 的附近鸭子、一个共享节拍、作为粗略距离的 RSSI、一个实时合成声音、来自 ToF 的手距离。

**形状比状态更重要。** 在场、心情和节拍是*一个大脑的输入*，不是它旁边的模式。合唱和特雷门琴长成显式模式，是因为没有大脑可挂——合唱是 `robotd` 的 55 KB——而那个正是这个里程碑存在要停止重复的模式。它在有代码前先有设计文档。

**完成当：** 一只独自留在房间里的鸭子做点值得看十分钟的事，且合唱是它决定的东西、而非命令启动的东西。

## 工作顺序

上面的数字是标识符。这是顺序。

1. **M8，策略通道。** 下一个特性。没有别的被它阻塞，而它解锁产出机器人实际行为的循环：训练、发布、安装、试用、回滚。
2. **M5 的传输调查。** 便宜，它的答案决定 Python 客户端是五十行还是一个项目。
3. **M6，随着发布临近**，按前置时间：客户机器人从哪下载、然后 PIN、然后恢复网的硬件测试。同意随时能落地、该早落地。
4. **M7**——一个没有日期的调查。它第一次在别人手里的鸭子出了没人能命名的故障时赢得优先级，而最便宜的准备好办法是把它和 #52 一起决定而非之后。
5. **M9，大脑**——之后、刻意地。它是剩下最大的工作、也最可能在构建中长大。
